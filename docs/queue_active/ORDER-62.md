# Active Queue Spec: ORDER-62

> Canonical status is indexed in `docs/CODEX_QUEUE.md`.

#### [ ] ORDER-62 [P0·기능 정리] 모든 기능에 킬링포인트가 있는가

**사용자 지시 (2026-07-30):** *"이 게임이 수시로 새 기능이 붙고 번복되고 다시
바뀌면서 죽은 코드나 기능이 많을 거야. 이제 목업 수준으로 만들면 안 돼. 모든
기능 하나하나 핵심적이고 킬링포인트가 있어야 해."*

**이 저장소는 죽은 데이터는 잘 잡고 반쪽 기능은 못 잡는다.** 휴면 콜백 564,
write-only 플래그 기준선 0 같은 데이터 감사는 촘촘한데, 기능이 진입점과 UI를
갖추고도 소비자가 없는 상태는 어떤 검사도 보지 않는다.

## 착수 전 이미 나온 증거

| 대상 | 상태 | 근거 |
|---|---|---|
| `scenes/TradingFloor.gd` | **죽음** | 806줄, 자기 파일 외 참조 0, 오토로드 미등록 |
| 단서 시스템 | **반쪽** | 지급 10선택·UI·엔진은 있는데 `has_clue()`를 부르는 게임 코드 0 |
| `mental` | **반쪽** | 사건 효과 3,007회 변경, 조건으로 읽는 곳 12 |

단서가 대표 사례다. 데이터 3종·한영 본문·지급 경로 10개·`단서 / 생각 정리`
UI·빈 상태 문구까지 있는데 **그 단서를 가졌다고 열리는 것이 하나도 없다.**
모으는 곳은 있고 쓰는 곳이 없다.

**판정이 어렵다는 것 자체가 문제다.** 이 세 건을 확인하는 데 스캔을 네 번
고쳐야 했다 — 엔진은 `choice.clues`를 읽는데 처음에는 `choice.effects.clues`를
봤다. 사람이 매번 이렇게 파야 한다면 반쪽은 계속 쌓인다.

---

## 1. 네 판정

살아있음과 죽음의 이분법으로는 사용자가 말한 목업을 잡지 못한다. **작동하는데
없어도 되는 것**이 목업의 실체다.

| 판정 | 뜻 | 조치 |
|---|---|---|
| **핵심** | 킬링포인트가 있고 실제로 작동한다 | 유지 |
| **주변** | 작동하지만 없어도 플레이어가 모른다 | **제거 후보** |
| **반쪽** | 킬링포인트가 될 수 있는데 소비자가 없다 | 완성 또는 제거 |
| **죽음** | 도달 불가 | 제거 |

기본값은 **미확인**이다. 확인하지 않은 기능을 살아있다고 가정하지 않는다.

## 2. 킬링포인트의 정의 — 이 게임 한정

작품은 관계 서사 게임으로 확정됐다. 따라서 기능은 아래 셋 중 최소 하나에
닿아야 한다. 닿지 않으면 장식이다.

1. **사람에게 시간을 쓰는 선택**을 만들거나 무겁게 한다.
2. **대가와 놓친 길**을 보이게 한다.
3. **같은 사람으로 남는가**라는 질문에 관여한다.

`재미있다`, `있으면 좋다`, `다른 게임에 있다`는 킬링포인트가 아니다.

## 3. 삭제 테스트

기능마다 지운다고 상상하고 무엇이 깨지는지 적는다.

```
정본 계약이 깨진다              →  핵심
다른 핵심 기능이 깨진다          →  핵심
플레이어가 알아채지 못한다        →  제거
아무것도 안 깨지는데 지우기 아깝다  →  그것이 목업이다
```

**마지막 줄이 이 오더의 핵심이다.** `지우기 아깝다`는 근거가 아니다. 만드는 데
든 시간은 유지할 이유가 되지 못한다.

## 4. 기능 원장

`docs/FEATURE_LEDGER.md`를 만들고 플레이어가 만나는 모든 기능에 한 행씩 준다.

```
기능 | 진입점 | 실행 | 산출물 | 소비자 | 킬링포인트 | 판정 | 마지막 사람 확인
```

**진입점·실행·산출물·소비자 중 하나라도 비면 반쪽이다.** 이 저장소가 이미
플래그에 적용하는 규칙(`생산자와 실제 독자를 함께 가져야 한다. write-only·
inert 기준선은 0`)을 기능 단위로 올린 것이다.

단서를 첫 행으로 채운다. 킬링포인트는 **아버지를 무너뜨린 것이 누구인지
플레이어가 스스로 알아낸다**이며, 소비자 0이라 그 킬링포인트가 작동하지
않는다. 따라서 판정은 `반쪽`이고 제거가 아니라 완성 대상이다.

## 5. 도구화

`tools/feature_liveness_audit.py`를 만든다. 원장이 손으로만 유지되면 반드시
낡는다.

- 원장의 각 행이 선언한 진입점·소비자가 **실제로 존재하는지** 검증한다.
- 원장에 없는 신규 기능 파일을 발견하면 보고한다.
- **참조 0인 `.gd` 파일을 보고한다.** `TradingFloor.gd`가 지금 그 상태다.
- 설정 키 중 읽는 곳이 없는 것을 보고한다.
- 기준선 래칫 — 반쪽·죽음의 수가 늘면 실패다.

`audit_scope.json`에 등록한다. 미등록 검사는 `--verify`가 잡는다.

## 6. Codex 판단 규칙 — 정본화

`이런 것도 필요하겠는데?`는 취향이며, 취향으로 기능을 늘리면 반쪽이 늘어난다.
단서가 그렇게 생겼을 가능성이 높다.

**근거는 취향이 아니라 정본이다.**

```
필요하다   →  "정본 X가 Y를 요구하는데 구현이 없다"
불필요하다 →  "요구하는 정본이 없고, 지워도 아무것도 깨지지 않는다"
```

둘 다 **정본 인용이 있어야 성립한다.** 인용할 정본이 없으면 판단이 아니라
의견이고, 의견은 만들지 말고 `POST_LAUNCH_NOTES.md`에 기록한다.

`CODEX_QUEUE.md`의 `사전 승인 대기 항목`에 한 줄을 더한다.

> **반쪽 기능을 발견해도 완성할지 제거할지 스스로 정하지 않는다.** 원장에
> 기록하고 판정을 받는다. 반쪽을 자기 판단으로 완성하는 것은 수리처럼 보이는
> 오더 밖 신규 작업이며, 이 저장소가 반쪽을 쌓아 온 경로다.

## 배치

| 배치 | 내용 |
|---|---|
| 1 | 기능 인벤토리 — 플레이어가 만나는 기능 전수 목록화. 판정은 아직 |
| 2 | 판정 — 네 판정과 킬링포인트를 각 행에 적용. **제거는 아직 하지 않는다** |
| 3 | 사용자 판정 뒤 제거·완성 — 배치 2의 목록에서 승인받은 것만 |
| 4 | 도구화 + Codex 판단 규칙 정본화 |

**배치 2까지가 조사다.** `ORDER-60`과 같은 이유로 조사와 수리를 섞지 않는다.
제거는 되돌리기 어렵고 킬링포인트 판정은 작품 판단이므로, **어떤 제거도
사용자 승인 없이 하지 않는다.**

## 금지·보존

- 배치 3 전에는 어떤 파일도 지우지 않는다. `TradingFloor.gd`도 포함이다.
- 반쪽을 발견해도 그 자리에서 완성하지 않는다.
- 저장 호환, 엔딩 ID, 사용자 소유 `project.godot`은 건드리지 않는다.
- 기존 정본을 이 오더에서 고치지 않는다.
