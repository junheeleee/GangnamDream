# Active Queue Spec: ORDER-116

#### [~] ORDER-116 [P0·서사 구조] career 결말을 서류 절차가 아니라 실제 업무 책임으로 다시 설계한다

**사용자 지시 (2026-08-20):** M01~M60 원고와 ORDER-114/115 계약에 대한 사람 판정에서
마지막 해 career·startup이 같은 계약 처리 16칸을 반복하고, 선택 절반이 기록·열람
형식으로 수렴하며, 플레이어 산문에 상태 코드가 노출된 문제가 확인됐다. R1b는
ORDER-112·113 구조가 사람 판정을 통과할 때까지 열지 않는다.

## 착수 선언

- 상태: `[~] 구조 설계 중`
- 기준: `main@803a372`
- 이번 배치의 판정 단위: career 16개 사건 구조 +
  `arc_y5_father_trace_passed_missed` 선택 구조 1개 = **17단위**
- 만지는 파일: `CLAUDE.md`, `docs/CODEX_QUEUE.md`, 이 사양,
  `docs/WORK_LOG.md`, 재생성 `docs/STATUS.md`
- 수정하지 않는 파일: 사건 KO·EN JSON, `story_map.json`,
  `year5_reference_routes.json`, R1a kernel/check, GameState·save·dispatcher,
  endings·번역·아트·오디오

## 깊이 3문

1. 현재 career는 계약 열기→검토자 전달→경계→검토→4인 회의→수정→접수→
   사본 전달→판정→실행→사본 전달→서명이라는 문서 custody pipeline이다.
   startup도 같은 순서와 역할을 16/16으로 반복한다. 숫자와 명사만 바꿔서는
   다섯 해의 다른 결말이 되지 않는다.
2. career의 고유 질문은 “어느 조항을 기록할까”가 아니다. 직책을 받은 뒤 실제
   업무 위기에서 누구의 밤을 태우고, 품질·기한·사람 중 무엇을 포기하며,
   그 결과를 본 뒤 직책을 유지·반납·퇴사할지를 고르는 것이다. 문서는 결과
   영수증이어야 하며 주 플롯이 아니다.
3. R1a가 잠근 9 roots·25 choices·선형 cursor·두 blocker는 반려된 원고의
   구조다. 이번에는 새 구조를 문서로만 판정하고, 사람 GO 전 원고·manifest·
   kernel·저장 배선으로 굳히지 않는다.

## 이번 배치의 완료물

### A. career 16단위 topology

- M49~M60을 `직책 제안 → 실제 업무 투입 → 업무 위기 → 사람·기한·품질 배분 →
  결과 목격 → 책임 인수/직책 반납/퇴사 → 다음 월요일`의 고유 리듬으로 다시 놓는다.
- 각 단위는 장소, 지금 벌어지는 사건, 실제 동석 인물, 선택 2~4개, 즉시 비용,
  닫히는 길, 다음 독자를 가진다.
- 검토본 전달·사본 전달·어느 줄을 먼저 읽을지는 선택이 아니라 장면 결과 또는
  압축된 연결 동작으로만 둔다.
- startup의 동일 월 장면에 명사만 바꿔 이식할 수 있는 단위는 실패다.

### B. 선택층 판정

각 선택은 아래 네 질문에 답해야 한다.

1. 지금 비용을 내는 사람은 누구인가.
2. 지금 잃는 시간·돈·권한·관계는 무엇인가.
3. 이 선택으로 다시 고를 수 없게 되는 길은 무엇인가.
4. 왜 이 선택을 startup 경로에 그대로 옮길 수 없는가.

답이 어느 줄·매체·문서·순서로 남기는지뿐이면 반려한다. 표현 선택은 저장값이
없어도 민준의 목소리와 상대의 고유 반응이 실제로 달라질 때만 허용한다.

### C. 아버지 흔적 1단위

`arc_y5_father_trace_passed_missed`의 필사·녹음·촬영 3택을 폐기한다. 확인된
`응답 없음·연결 0:00`은 결과 물성으로 남기고, 선택은 남은 하루를 누구에게 쓰는지,
어떤 의무를 미루는지, 무엇을 끝내 포기하는지에서 갈라지는 새 구조로 설계한다.
인물 생사·통화 사실·미접수 자기 명의 초안은 기존 정본을 바꾸지 않는다.

### D. 코드형 표면 정책

- `NOT USED`, `SELF ONLY`, 문서 내부 ID, hash suffix는 상태·계보 데이터에만 둔다.
- 플레이어 산문은 사람의 행동, 날짜, 서명 유무, 빈칸, 같은 종이인지 확인할 수
  있는 물성으로 쓴다.
- 실제 원고 교정 범위와 KO·EN 대조는 topology GO 뒤 별도 15~25단위 배치가 소유한다.

## 구조 L3 게이트

- 무작위 3편만 보지 않는다. career의 전제·중간 위기·최종 결과 3단위를 고르고,
  기존 startup의 같은 월 장면과 나란히 읽는다.
- 고정 실패 감지 표본으로 아버지 흔적 1단위를 함께 읽는다.
- 한 단위라도 startup에 명사만 바꿔 이식 가능하거나 선택 비용·닫힌 길을 설명할
  수 없으면 17단위 전량 반려한다.
- GO 뒤에도 즉시 R1b로 가지 않는다. career 실제 원고→career L3→startup topology→
  startup 실제 원고·L3→manifest v2→kernel v2 순서로 진행한다.

## 검증·보호

- L1: 17단위 존재, 단위별 장소·사건·배우·선택·비용·닫힌 길·독자 완비,
  문서/매체 형식 선택 0, startup 1:1 슬롯 대응 0.
- L2: 인물 목소리, 실제 업무 구체성, 두 가치 이상 충돌, 결과 목격과 여운 판정.
- L3: 위 구조 표본 4개를 사용자 또는 사용자가 지정한 사람 판정자가 읽는다.
- `main@803a372` 사건·계약·kernel·runtime·save·endings는 byte-exact로 보존한다.
- 전체 감사·240주·엔딩 검사는 실행하지 않는다.

## 완료 조건

- 17단위 topology와 각 선택의 네 질문 답이 이 사양에 확정돼 있다.
- 기존 ORDER-112·113과 R1a는 `L3 rejected / reference-only frozen`으로 명시된다.
- 독립 구조·문학 L2가 P0/P1 0을 내고, 사람 L3 전에는 원고 구현을 시작하지 않는다.
